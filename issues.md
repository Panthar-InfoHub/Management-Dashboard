Security — critical
1. The Clerk webhook silently defeats your invite-only signup. route.ts:23-56 creates an ACTIVE Employee with role EMPLOYEE for every user.created event. Meanwhile auth.ts:75-83 deliberately blocks uninvited signups with INVITATION_REQUIRED — but that guard only runs when no Employee row exists, and the webhook creates one first. Since /sign-up is public in proxy.ts:14, anyone who can self-register in your Clerk instance becomes a full active employee (directory access, teams, kanban) without any invitation. The webhook also uses email_addresses[0] with no verification check — the exact risk the comment in auth.ts:45-47 warns about. The webhook should apply the same rule as the JIT path: link only to pre-provisioned employees by verified primary email, otherwise do nothing (or delete the Clerk user).

2. Account-takeover primitive in createEmployeeAction. employee.actions.ts:41-52: if a Clerk user already exists for the submitted email (and there's no active DB row), the action sets that Clerk user's password to a caller-supplied value and unbans them. Anyone holding employee:create can seize any Clerk account that isn't currently an active employee — e.g. an offboarded user whose Clerk deletion failed (that failure is swallowed at employee.actions.ts:465), or any stray account in the instance. Re-inviting should never overwrite credentials; drop the updateUser({ password }) branch entirely.

Security — high
3. user.updated webhook lets a user rewrite their own Employee.email to an unverified address. route.ts:59-72 copies email_addresses[0] (not necessarily primary, not necessarily verified) into the unique email column — which is the key the invite-linking logic in auth.ts trusts. A user adding someone else's email as an unverified secondary address can poison that mapping. Sync only the verified primary address (primary_email_address_id).

4. Task assignees can move tasks across project boundaries and reassign anyone. In task.actions.ts:74-97, a user with no task:update permission — merely an assignee — passes the ownership check and then may set projectId to any project (no membership check on the target) and assignees.set to any employees. That's cross-project write access and lets a low-privilege user inject tasks into projects they can't even view. assignTaskAction (task.actions.ts:246-250) has the same shape for creators. Validate the target project membership and restrict who non-privileged users may assign.

5. employee:update escalates to full Manager power via hardcoded role names. Data visibility is gated by literal role === "ADMIN" || role === "MANAGER" checks (employee.queries.ts:6, dashboard.queries.ts:9-11, plus invite links/offboarding/codes in employee.actions). But updateEmployeeAction only blocks assigning ADMIN or roles carrying role:manage — assigning the literal MANAGER role is allowed. So a non-admin with just employee:update can promote themselves-adjacent accounts (or via transitionRoleAction, any employee — it has no role-escalation guards at all, see employee.actions.ts:364-398) to MANAGER and unlock all PII and org-wide views. transitionRoleAction skipping every check that updateEmployeeAction enforces (ADMIN target, self-change, role:manage roles) is the sharpest edge here.

Security — medium / hygiene
deleteEmployeeAction (employee.actions.ts:235) has no self-delete guard and hard-deletes (cascading employment records and notifications), unlike the careful offboard path.
Clerk invitation list pagination bug: getInvitationList({ status: "pending" }) returns only the first page (default 10). The dedupe in employee.actions.ts:77, the lookup in getInvitationLinkAction:354, and the revoke in offboard:471 all silently miss invites past the first page — a correctness/authz gap (stale invites survive offboarding).
.env.local is open in your IDE and gitignore is correct, so nothing is committed — good — but double-check it was never committed historically.
Performance
getKanbanTasks never returns blockedById/subtasks but loads full assignee+project per task on page 1 of 50 — fine — but the board's revalidatePath("/", "layout") on every status/priority drag (task.actions.ts:140,168,194) invalidates the entire app layout cache, forcing every dashboard query to refetch. Scope revalidation to /tasks and the specific project.
getProjectById / getProjectsList load every task with all assignees just to compute a progress percentage (project.queries.ts:25,54). For projects with many tasks this pulls large payloads to the server to do a count you could get with _count + a grouped status count. Same pattern in getDashboardProjectsSummary.
getDashboardChartsData (dashboard.queries.ts:195-208) fetches every non-done task's nested project→team just to count per team in JS. This should be a groupBy/raw aggregate like getCompletionTrend already does.
Repeated getCurrentEmployee + checkPermission per query: each page calls several queries that each call getCurrentEmployee() and checkPermission(), and each checkPermission does its own systemRole.findUnique. getCurrentEmployee is cache()-wrapped (good), but hasPermission is not — the same role's permissions are re-fetched many times per request. Wrap hasPermission/getPermissionsForRole lookups in react's cache().
chart.tsx uses dangerouslySetInnerHTML (chart.tsx:95) — this is the stock shadcn chart theming with static color config, not user input, so it's not exploitable, just flagging that I checked it.
